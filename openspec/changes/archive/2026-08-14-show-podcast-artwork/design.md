# Design: show-podcast-artwork

## Context

アートワークのデータ層は MVP で実装済み:購読・手動更新時に `ArtworkStore.ensureCached()` が画像を `<外部ファイル領域>/artwork/<feedId>.img` へ保存し、パスを `feeds.artworkLocalPath` に永続化、購読解除時にファイルも削除する。未取得の番組は `refresh()` のたびに再試行され、取得済みの番組は二度と通信しない。一方、表示側は未実装で `ArtworkStore.load()` の呼び出し箇所はゼロ。playback spec の「プレイヤー画面はアートワークを表示する(SHALL)」も未実装のまま乖離している。

表示対象は3画面:購読一覧(行ごと)・エピソード一覧(ヘッダーに1枚)・プレイヤー画面(大きく1枚)。

## Goals / Non-Goals

**Goals:**

- キャッシュ済みアートワークを3画面に表示し、番組をパッと見で識別できるようにする
- 画像の無い・読めない番組を異常扱いせず、モノグラムで統一的に代替表示する
- 表示による通信・OOM・UI スレッドブロックを発生させない
- 判断(縮小率算出・頭文字選定)を `logic/` の純粋関数に置き、JVM テストで固める

**Non-Goals:**

- アートワークの取得経路・鮮度の変更(データ層は変更しない)
- MiniPlayer・Media3 通知への表示
- エピソード個別アートワーク
- 画像ライブラリの導入

## Decisions

### D1: 表示時に縮小デコードし、ViewModel のメモリ内に保持する

ディスクには元ファイルだけを置き、表示時に目標ピクセルサイズへ `inSampleSize` 縮小デコードする。結果は ViewModel の `Map<feedId, Bitmap>`(購読一覧)や単一 StateFlow(エピソード一覧・プレイヤー)に保持し、再コンポジション・画面回転では再デコードしない。デコードは `Dispatchers.IO`。

- 代替案「ダウンロード時に縮小版ファイルを事前生成」は不採用。必要サイズが3種類あり、サイズはコード内定数のため定数変更時に既存縮小版が古くなる「再生成」問題を自分で作ることになる。節約できるのはプロセス起動後初回の数十ms×十数枚だけで、複雑さが利益を上回る
- 代替案「毎回フルデコード」は不採用。3000×3000px の画像は1枚 36MB になり OOM の実リスク

### D2: 縮小率の算出と頭文字の選定は `logic/` の純粋関数

- `(元の幅・高さ, 目標ピクセル) → inSampleSize(2の冪)` の算出関数
- `番組タイトル → モノグラム表示文字` の選定関数(空白始まり・サロゲートペア・空文字で例外を出さない)

どちらも Android API 非依存で、Kover 90% ゲート配下の JVM ユニットテストで端ケースを固める。`BitmapFactory` を触る実行部(`ArtworkStore`)は薄く保つ。

### D3: 画像なし・破損は頭文字モノグラムに一本化する

`artworkUrl` 未申告・取得失敗継続・キャッシュ破損(`decodeFile` が null)のすべてを「Bitmap が得られない」という同一状態に落とし、番組名の頭文字+既存パレット単色(`secondaryContainer` 系)のタイルで代替する。取得失敗は設計上の通常状態(失敗しても購読は成功する)なので、エラー表示はしない。色を feedId から導出する装飾はしない。

### D4: エピソード一覧は TopAppBar に1枚。行には置かない

エピソード行の左端は DL/再生アクションが占有しており(3つのタップ領域の1つ)、行に画像を足すと機能と装飾が衝突する。また同一番組の画面で全行に同じ画像を繰り返しても識別情報は増えない。TopAppBar の title スロットを Row(画像 40dp, Column(番組名, feedUrl)) に差し替え、`EpisodeRow` は一切変更しない。TopAppBar は固定型なのでスクロール中も画像が見え続ける。feedUrl の移設(購読一覧の行からの削除の受け皿)も同じ箇所に合流する。

### D5: プレイヤー画面の配線は既存 `observeFeed` を使う

PlayerViewModel が持つのは `currentEpisode` だけなので、`episode.feedId` から `FeedRepository.observeFeed()` で Feed を引いて `artworkLocalPath` に到達する。これが本 change 唯一の新しいデータ配線。表示位置は縦スクロール Column の先頭(タイトルの上)で、レイアウト構造は変更しない。

### D6: 表示サイズはコード内定数

購読一覧 56dp・エピソード一覧ヘッダー 40dp・プレイヤーは画面幅基準。設定画面は作らない(プロジェクト方針)。デコード目標ピクセルは表示 dp から換算して渡す。

## Risks / Trade-offs

- [巨大画像による OOM] → D1 の縮小デコードで回避。フルサイズ展開の経路を残さないよう、一覧系は必ず目標サイズ付きの読み込みだけを使う
- [キャッシュファイル破損] → `decodeFile` の null をモノグラムへフォールバック(D3)。クラッシュ経路なし
- [TopAppBar の2行 title で高さが窮屈になる] → 番組名 1 行 + URL 1 行(bodySmall)+ 40dp 画像は標準高さに収まる想定。収まらなければ `TopAppBar` の高さ調整ではなく文字サイズ・行数の調整で対応(実装時に実機確認)
- [`ArtworkStore` の縮小デコードは JVM テスト不可(BitmapFactory は Android 依存)] → 判断は D2 で `logic/` へ寄せ、`ArtworkStore` は計装テストまたはスモーク相当に留める(既存のテスト方針どおり)
- [プロセス死直後の初回表示でデコード分の遅延] → IO スレッドで非同期に読み、完了までモノグラム(または空)を出す。十数枚×数十msで体感影響なし
