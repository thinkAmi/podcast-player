# 設計: エピソード詳細とプレイヤー画面の統合

## Context

現状は4画面構成のうち2枚(エピソード詳細・プレイヤー)がほぼ同じ表示を持つ。

- 詳細画面(`episodes/{episodeId}`)は episodeId で指名される読み物。未DLでも開ける。再生状態と無関係
- プレイヤー画面(`player`、引数なし)は「いま鳴っているもの」に追随し、キュー終端で自動クローズする。自動クローズは「エピソードIDの非null→null遷移」の検出と二重popガードという繊細なコードで成立している(`PlayerScreen.kt` の LaunchedEffect)
- 再生開始は一覧の行アイコンのみ。キューはフィルター適用後の表示順から `PlaybackQueue.playbackOrderFrom` で組む。フィルターは Feed として DB に永続化されているため、一覧以外の場所からも同じ順序を再現できる
- 視聴済みトグルは一覧の行のみ。player 層は played の変化を一切見ておらず、再生中のエピソードを視聴済みにしても再生は続き、猶予後に鳴っている最中のファイルが削除される(潜在地雷)

本設計は 2026-08-14 の探索セッションで利用者と合意した決定(状態一致追随・自動クローズ廃止・視聴済み=停止の統一)を実装可能な形に落とす。

## Goals / Non-Goals

**Goals:**

- 画面の種類を1つ減らし、ショーノート表示・再生コントロールの重複を解消する
- 「読む→DLする→聴く」を統合画面1枚で完結させる
- キュー終端の自動クローズ検出という繊細なコードを削除し、誤認リスクのある判定をゼロにする
- 「再生中のエピソードを視聴済みにする」の意味をアプリ全体で「停止+猶予付き削除」に統一し、再生中ファイル削除の地雷を解消する

**Non-Goals:**

- 「次へスキップ」ボタンの追加(視聴済み化の停止作用で代替。次を聴くかは一覧で決める)
- Undo による再生の自動復元(記録のみ戻す。再生再開は▶1タップで保存位置から可能)
- プレイヤー機能自体の変更(シークバー・±10秒・速度・Media3 の結線は現状維持)
- 一覧行の見た目の変更(LeadingAction の状態機械は共有するが行の表示は変えない)

## Decisions

### D1: 画面のアイデンティティ — 状態一致で追随、実装は nav 置き換え

統合画面は `episodes/{episodeId}` の一枚岩で、モードを持たない。「表示中のエピソード S = 現在のエピソード C」のときだけ追随する。

- 追随は表示の差し替えではなく、**nav エントリを `episodes/{次のID}` に置き換える**(スタックに積まない)。route は常に表示と一致し、プロセス復元は nav 引数から素直に行える。back スタックも肥大しない
- 追随のトリガーは「C が S から別の非null値へ遷移した」こと。非null→非null 遷移には controller 再接続時の誤認問題が構造的に存在しない(再接続の初期状態は null→非null)
- キュー終端(C が null になる)では何もしない。画面は留まり、エピソードの現況を映す(聴き終えた回は視聴済み+DL削除済みになるため、自然に「ノートのみ」の姿になる。これは一覧から視聴済みの回を開いたときと同じ表示であり、新しい状態ではない)

代替案と棄却理由:
- 入口(ミニプレイヤー経由か否か)でモードを分ける → 同じ画面が来歴で違う振る舞いをする隠れモードになる
- route を固定用と追随用の2つ残し View だけ共有 → 体験は維持できるが、route 削減と自動クローズ削除という引き算を諦めることになる
- 自動クローズの維持 → 「非null→null」検出と二重popガードを統合画面に持ち込むことになる。利用者はほぼバックグラウンド再生で、終端に画面を開いたまま立ち会うことは稀なため、稀なケースのために繊細なコードを維持しない

### D2: アクション領域 — 一覧行 LeadingAction と同じ状態機械の拡大

統合画面のアクション領域は新しい状態を発明せず、`EpisodeRow.kt` の LeadingAction が持つ判断(DL中→進捗 / 現在→トグル / DL済み→再生 / 失敗→再試行 / 未DL→DL)をそのまま使う。

- 「どの状態で何を出すか」の判断を composable から切り出して共有し、一覧と統合画面で挙動がズレる事故を構造的に防ぐ。判断部分が純粋になるなら `logic/` に置く
- 現在のエピソードのときだけ、アクション領域の代わりにフルコントロール(シークバー・±10秒・速度)を展開する
- DLの回線確認(モバイル回線時のダイアログ)・進捗表示・失敗時の手動再試行は一覧と同じ規則。確認ダイアログの状態は統合画面の ViewModel が持つ(一覧の `DownloadConfirmation` と同型)
- 再生開始は一覧の `play()` と同じ規則: DB 保存のフィルターから表示順を再現し、`PlaybackQueue.playbackOrderFrom` でキューを組む

### D3: 視聴済みトグル — 再生中は「停止+猶予付きUndo」、アプリ全体で統一

- 非再生中のエピソード: 従来通り(記録の切り替え+猶予付きUndoスナックバー)
- 再生中のエピソード(S = C): 視聴済み化 + キューを空にして停止 + 猶予付きUndoスナックバー。統合画面ではさらに前の画面へ pop する。この pop はボタンハンドラ内の直接操作であり、自動クローズのような検出は不要
- Undo は記録だけ戻す(played 復元+削除中止)。再生は自動再開しない。誤タップからの復旧は▶1タップ(`resumePositionMs` により保存位置から再開される。played=false に戻るため位置が使われる)
- 一覧の再生中の行のトグルにも同じ停止作用を足す(画面遷移はなし)。「再生中の回を視聴済みにする」の意味が場所によって変わらないようにする
- 停止が削除より必ず先行するため、「鳴っている最中のファイルを猶予後に削除する」経路が消える。`ListeningRules.shouldDeleteDownload` に再生中保護を足す必要はない(判断と実行の分離を保つ)

代替案と棄却理由:
- 事前確認ダイアログ方式 → 一覧トグルの「即実行+Undo」と同意の仕組みが二重になる。誤タップ対策は既存のUndo基盤で足りる(利用者合意済み)
- 視聴済み化で次の回へ自動前進 → 「次も聴きたいか」は利用者が一覧で決めたい(利用者合意済み)

### D4: pendingUndo の共有スコープ化

統合画面で「視聴済み+停止」を実行すると pop で前の画面に戻るため、Undoスナックバーは遷移先で表示され続ける必要がある。現在 `pendingUndo` は `EpisodeListViewModel` のローカル状態なので、ミニプレイヤーと同様に app スコープ(`PodcastPlayerApp` 直下で1つ)へ引き上げ、どの画面のスナックバーホストからも読めるようにする。

- 一覧のUndo(一括視聴済み等)も同じ共有状態に乗せ、Undo の置き場所を1つにする
- 猶予の確定(`commitPendingUndo`)・取り消し(`undoPending`)のロジックは現行を流用する

### D5: ミニプレイヤーの表示規則 — 「再生中かつ S≠C」のときだけ表示

- 隠す条件を「route == player」から「backstack の現在エントリが `episodes/{id}` で、id == 現在のエピソードID」に変える。判定式が D1 の追随条件と同じになり、「S=C なら画面自身がプレイヤー、S≠C なら読み物+ミニプレイヤー」という1つの理屈で説明できる
- タップは push 遷移を維持(別の回のノートを読んでいる途中で現在の回へ飛んでも、back で読みかけに戻れる)

### D6: ViewModel の構成

- `PlayerViewModel` は app スコープのまま残す(ミニプレイヤーと currentEpisode/status の共有、シークバー用 500ms ティックの持ち主)
- 統合画面の ViewModel は現行 `EpisodeDetailViewModel` を拡張し、episodeId に加えて playback・downloader・networkState・feedRepository・artworkStore を受け取る。S=C 判定・キュー構築・DL確認・視聴済み操作を担う
- 追随(nav 置き換え)は「C の遷移」を UI 層で観測して navigate する。ViewModel は nav を知らない(現行の onBack コールバック方式を踏襲)

## Risks / Trade-offs

- [キュー終端に画面を開いたまま立ち会うと、コントロールがその場で消えてノートのみの姿になる] → 受容する(利用者合意済み)。エピソードの現況を映しているだけで、一覧から視聴済みの回を開いたときと同じ表示。バックグラウンド中心の利用では最稀ケース
- [フィルターで除外された回(例: 「未聴のみ」フィルター中の視聴済み+再DL済みの回)で再生ボタンを押すと、キュー構築元の一覧に自分がいない] → `playbackOrderFrom` が空を返す既存挙動に乗せ、既存の「ダウンロードしてから再生できます」と同種のフォールバック文言を出す。稀なケースに構造を足さない
- [追随の nav 置き換えが画面遷移アニメーションとして目に見える可能性] → 置き換え遷移のアニメーション指定で抑制する。実装時に実機確認
- [「視聴済み=停止」への変更で、一覧トグルの挙動が従来と変わる(再生中の行のみ)] → スナックバー文言に「再生を停止しました」を含め、何が起きたかを明示する
- [統合画面 ViewModel の肥大化(detekt の LongMethod/LongParameterList)] → 状態判断を D2 の共有ロジックへ寄せ、ViewModel はグルーに保つ

## Migration Plan

1. 共有部品の抽出(アクション領域の状態判断、pendingUndo の共有化)— 既存挙動を変えずに移す
2. 統合画面の実装(詳細画面へプレイヤー要素と3状態アクションを吸収)
3. nav の切り替え(`player` route 廃止・ミニプレイヤーのタップ先変更・追随の nav 置き換え・ミニプレイヤー表示規則)
4. 視聴済み=停止の統一(統合画面+一覧の両方)
5. `PlayerScreen.kt` と自動クローズ検出の削除

`installDebug` の上書きインストールで購読・視聴状態・DLファイルは保持される。DB スキーマ変更はなし。ロールバックは前コミットのビルドを入れ直すだけ。
